# Replayer

Open **Mods > Balatro Observer > Config > Load Log** to choose a Multiplayer `.log` using the Windows file picker. Dropping a log onto Balatro also works. Use **Next run** for logs containing multiple manifests, then **Start Replayer**. Start creates a new seeded run, replacing the current run if one is open. Playback begins after the new deck and Action Recorder are initialized. **Stop Replayer** stops further input. Return to the main menu to end the replay session and restore prior practice settings.

For Cocktail, the recorded pool/forced-deck settings temporarily replace Multiplayer's offline Cocktail configuration. Multiplayer builds and applies the combined deck from that configuration and the recorded seed. The original settings are restored when the session ends. A different installed deck-pool size is rejected.

Replayer uses Multiplayer's installed ghost engine for opponent scores and an Observer input driver for local actions. The manifest selects seed, deck, stake, ruleset, modifiers, and existing lobby gameplay options including Cocktail. It requires the recorded Multiplayer version, the deck/ruleset, and matching opponent history. Other installed gameplay mods should match the original environment; missing historical card identities or differing mod behavior can prevent exact reproduction.

Only `MP_RLOG:` lines drive a replay; Multiplayer's mirrored human-readable stream is never read. Play, discard, buy, sell, use, reroll, pack selection/skipping, blind selection/skipping, and reorder pass through Action Recorder. Ante keys, PvP readiness and received asteroids drive the replay too. Cash-out and shop exit are inferred transitions because Multiplayer does not log them. A `use` records a slot but not an area, so every one is resolved before the run starts from the action stream alone: a use carrying hand targets is a consumable, one answered by a pack pick or skip opened a booster, and the rest are settled at runtime by which areas hold that slot and what the game will accept. Every action in the log is resolved before the run starts; during playback an action the run cannot perform is skipped and counted rather than ending the session, and the final status reports how many were skipped and how many cards came out different. This is not proof of deterministic equivalence: positional logs contain no card identity checkpoints for most actions, so a run whose pools differ will drift and still play to the end.

Replay sessions disable saving and block Multiplayer Client.send. Importing never executes code from a log. No log contents are committed or transmitted. Status is shown in config, in the Balatro log and in `%APPDATA%/Balatro/balatro_replayer/status.json`; a stalled action reports its opcode and the game state it waited in. Export the resulting run through **Open Action Recorder**.
